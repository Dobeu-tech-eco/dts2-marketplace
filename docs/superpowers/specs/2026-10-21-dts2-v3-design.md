# dts2-harness v3 — Design

Date: 2026-10-21. Status: pending approval (all reviewer questions resolved). Repo: Dobeu-tech-eco/dts2-marketplace, plugin `plugins/dts2-harness` (current 2.2.0; this design ships as 3.0.0).

## 1. Intent

dts2-harness is Jeremy's plan → build → review → verify coding harness, installed from a public marketplace so any machine gets it with `/plugin marketplace update dts2`. v2 works; v3 makes it something he can grow without friction, run from onboarding to a known "end state", and trust to hold itself to a written discipline.

The guiding split, decided in conversation:

- **`setup` interviews the user to a measured end state.** It does not stop at config files. It ends when the harness can state what "done for this repo" means with a clarity score above a threshold.
- **`run` does every slice between here and that end state**, and quietly keeps the setup state current. The user never sees the state-keeping machinery.
- **Internals never leak.** Worktrees, lanes, tiers, and gates are implementation. In a single repo the user hears about none of them unless something needs a decision.

Everything in this design ships inside the plugin folder so the public marketplace stays the only install path.

## 2. Goals, non-goals, anti-goals

Goals
1. Extending the harness itself is a supported, named action with a known home (G1).
2. Machine-prep offers three pruning levels backed by real usage data and finds redundant plugins (G2).
3. The two human approval points are named plainly, worded as decisions, and consistent between interactive and headless runs (G3).
4. Onboarding reaches a scored end state, with a round to paste related/linked repos (G4).
5. The pipeline can hand roles to Codex, Cursor, Antigravity (and others) by specialty, from one roster (G5).
6. Rule 8, Harness discipline, is enforced by the harness, not just documented (G6).
7. Review includes security, a UX critique that never edits, and a screen-by-screen browser walkthrough (G7).
8. A one-pass go-to-market review orchestrates the already-installed marketing-skills plugin (G8).

Non-goals
- Re-implementing deep-interview, Impeccable, or marketingskills. We adopt their patterns and, where installed, call them.
- New agents. The agent budget is 6 (lead, builder, reviewer, verifier, scout, auditor) and stays there.
- A GUI. Everything is skills, agents, hooks, scripts, and files in the repo.

Anti-goals (would make v3 a failure even if it "works")
- Worktree or lane language appearing in a single-repo session.
- A review phase that edits code.
- A run that commits, pushes, or opens a PR without an explicit yes at the ship checkpoint.
- Copying upstream prompt text into the plugin. Patterns yes, text no.

## 3. Constraints

- Plugin structure rules: `.claude-plugin/plugin.json`, components at plugin root, kebab-case names, no "claude"/"anthropic" in skill or plugin names, `${CLAUDE_PLUGIN_ROOT}` for all intra-plugin paths.
- Agent budget 6 (`profiles/blueprint.json` → `claudePluginAgents`). New capability goes into skills and reviewer axes, not agents.
- Works on Windows, WSL (wrapping Windows claude.exe), Linux, macOS. Scripts are Python 3 stdlib; hooks are POSIX sh.
- Nothing in the plugin reads credential files or writes keys.
- Upstream licenses: oh-my-claudecode MIT, Impeccable Apache-2.0, marketingskills MIT. Attribution goes in `README.md` → Acknowledgements.
- Code style (from Jeremy's standing preferences): explicit types, one export per file, named constants, functions under ~20 lines, early returns.

## 4. The parts, as decided

### 4.1 `evolve` skill and the scope fix (G1)

New skill `skills/evolve/SKILL.md`: "change the harness itself".

- Locates the plugin source: `git remote` match on `dts2-marketplace`, else `~/.dts2/marketplace`, else clone `Dobeu-tech-eco/dts2-marketplace` to `~/.dts2/marketplace`. Never edits the install cache.
- Applies the change there, runs `claude plugin validate`, bumps the version in both manifests, commits with a conventional message. Pushes only on explicit yes. Prints the two-command update.
- `run` gains a preflight rule: if the request names a harness skill, agent, hook, or profile, route to `evolve` and say so in one line. It never plans a harness change as a repo task.

Scope wording in `run`: worktrees exist only when `profile.workspace` is set (multi-repo) or the user has opted in with `use_worktrees: always`. Default for a single repo is `never`. Parallel builders in one repo work in the same tree on disjoint file sets (lanes already own files exclusively). The words "worktree" and "lane" do not appear in user-facing output in single-repo mode; the plan shows "N builders working on separate file sets".

`.gitignore` guard: `run`, `sdk`, and `gtm` call a shared `scripts/ensure-ignored.py` that idempotently appends `.harness/runs/`, `.harness/lessons-inbox.md`, `.harness.bak-*/`, `.claude/*.local.md`, `.harness/review/screens/`. Committed: `.harness/config.yaml`, `review-checklist.md`, `lessons.md`, `end-state.md`, `discipline.md`, `state.md`, `review/*.md`. My call: run logs and screenshots are noise; decisions and lessons are the record.

### 4.2 Machine-prep tiers and redundancy (G2)

`scripts/machine-prep.py` gains `usage` and tier flags.

Usage source: Claude Code session transcripts under `<claude home>/projects/*/*.jsonl`. The script reads only `tool_use` records named `Skill` and `Agent` (`subagent_type`) and `mcp__*` tool names, counts by plugin id over a window (`--days`, default 30 — my call). It never reads message text, and prints counts only.

Tiers (`--tier light|standard|strict`; the skill asks once):
- **light** — sync stays on; disable only plugins and skills with zero uses in the window and no `required` preference.
- **standard** — blueprint keep-set for marketplace plugins; synced plugins disabled per-plugin except a keep-list seeded from usage (top-N by count, N from profile, default 5).
- **strict** — `syncClaudeAiPlugins: false` and `syncClaudeAiSkills: false`; keep-set only. The skill states that skill-sync off also removes always-synced skills such as `pdf` and `xlsx`.

Redundancy report (all tiers): plugins whose `agents/` set hashes identical to another's (the seven 86-agent packs) → "keep one, disable N"; skills with identical names across plugins → list with the plugin ids. Recommendation only; the tier decides what is applied.

### 4.3 Checkpoint wording (G3)

Rename in all skills, agents, README, template, and the SDK runner:
- Gate 1 → **Plan checkpoint**: "Here is the plan, the done-criteria, and who does what. Approve, edit, or stop." Silence still means stop.
- Gate 2 → **Ship checkpoint**: "Here is the receipt. Ship, fix the blocking items and re-check, or stop and revert."

"Never skip either gate, even in auto mode" becomes: "Both checkpoints need a human. Headless runs stop at each and write what a human would have seen." The SDK runner gets a ship checkpoint: it writes `.harness/runs/<stamp>/receipt.md`, never commits, and exits 0/1/2 as the verdict. `--yes` approves only the plan checkpoint; a commit from headless requires `--ship` plus a CI branch guard (`DTS2_SHIP_BRANCH` must match). My call.

### 4.4 Onboarding to an end state (G4)

`setup` becomes a two-part skill: **interview**, then **scaffold**.

Interview, modeled on deep-interview's structure (not its text):
1. Detect greenfield vs brownfield. Brownfield: scout maps the repo first and reads any existing `.harness/`.
2. **Repos round** (Jeremy's addition, always before any component question): "Paste any other repos that matter here, one per line." For each URL the user says what the repo is and what it serves (stored as `role`), then tags it `context` (read-only reference the lead and builders may consult for conventions and contracts) or `linked` (joins a multi-repo workspace; triggers workspace mode and `.harness-workspace.yaml`). Stored in `end-state.md` → Related repos. Context repos are shallow-cloned to `~/.dts2/context/<owner>-<repo>` on demand, never into the project.
3. Topology round: propose 1–6 top-level components; user confirms, merges, splits, or defers; list locks.
2c. **Agents round** (Jeremy's addition): setup detects installed agent CLIs (`codex`, `gemini`, `opencode`, `gh copilot`, Cursor, Antigravity by their rules folders or binaries). If only Claude is present, the roster is `[claude]` and this round is a one-line note, not a question. Otherwise it proposes a roster from the detected agents with default roles and asks once.
4. One question per round at the weakest component × dimension (goal, constraints, success criteria; brownfield adds existing-context). Clarity score shown each round as a percentage. Threshold 80% (decided; settable in `.claude/dts2-harness.local.md` as `end_state_threshold`). Below threshold the interview continues; the only way past it early is the user typing "Continue anyway", which is recorded in `end-state.md` with the score at that point. Hard cap 20 rounds.
4b. **Skills round** (Jeremy's addition, after the interview and before scaffold): with every component and acceptance criterion known, the harness searches for skills that fit each component without installing anything — `find-skills` when present (search mode), else `npx skills find <component>`, else skip with one line. It shows at most 3 per component with source and a one-line reason, and asks which to install **for this project only** (project scope: `.claude/skills/` or the project `.claude/settings.json` `enabledPlugins`; never the user's global home). The output is a **skill plan**, not an install list: `end-state.md` → Skills is a table `skill | source | installed | serves component | phase (plan/build/review/verify) | order`. The lead reads this table and hands each builder the skills for its component in that order; reviewers get the review-phase skills. Declining installs nothing and the table records `installed: no`.
5. Writes `.harness/end-state.md`: metadata (rounds, clarity, threshold), related repos, topology, goal, constraints, non-goals, acceptance criteria per component, assumptions, open questions. Status `pending approval` until the user approves it, which is the scaffold step's gate.

Scaffold is today's setup plus `discipline.md`, `state.md`, and an `.agents/product-marketing-context.md` stub only if the repo has a marketing surface (detected: landing page, pricing page, or README with install/pricing sections).

`run` reads `end-state.md`, picks or accepts the slice, and after the ship checkpoint runs `learn` automatically (`auto_learn: true` default in `.claude/dts2-harness.local.md`; `false` turns it off) and updates the component's status and acceptance-criteria checkboxes and appends to `state.md`. These writes are part of the commit and are not narrated.

### 4.5 Agent roster and specialties (G5)

Roster chosen from current rankings (Morph leaderboard, updated 2026-10-06; Firecrawl comparison, 2026-08-03) crossed with the agents the `skills` CLI already targets, so each agent's rules-file convention is known. Seven profiles ship in `profiles/agents/`:

| Agent | Form | Rules file | Invocation | Default roles |
|---|---|---|---|---|
| claude (Claude Code) | CLI | `CLAUDE.md` | live | lead, verifier, builder, reviewer |
| codex (OpenAI Codex) | CLI | `AGENTS.md` | live | builder, second-opinion reviewer |
| gemini (Gemini CLI) | CLI | `GEMINI.md` | live | second-opinion reviewer |
| opencode | CLI, `opencode serve` headless | `AGENTS.md` | live | builder |
| copilot (GitHub Copilot) | CLI + cloud agent | `.github/copilot-instructions.md` | live (CLI) or handoff (cloud) | builder, reviewer:security |
| cursor | IDE | `.cursor/rules/*.mdc`, reads `AGENTS.md` | handoff | builder |
| antigravity | IDE | `AGENTS.md` (verify at build) | handoff | builder |

Cline, Goose, Aider, and Kilo Code are on the top-10 lists but not scaffolded; adding one is an `evolve` task with the same profile shape.

Each profile: `roles` it may hold, `invocation` (`live` via CLI/SDK with the command and headless flag, or `handoff` via generated files), `rulesFile`, `specialty` notes the lead reads when assigning, and `verified: true|false`. `.harness/config.yaml` → `roster:` lists which profiles are enabled and overrides roles. The lead assigns by specialty and never assigns a role the profile does not list.

Handoff lanes: the lead writes `.harness/handoff/<agent>/<lane>.md` plus the agent's rules file, and `run` pauses at that lane until the user reports it done. Rules files are generated via `npx skills add` conventions where that CLI supports the agent (claude-code, cursor, codex, github-copilot, gemini, antigravity, cline, amp, windsurf), so the harness never hand-maintains those formats. `sdk/dts2-run.py` already routes codex|gemini second opinions; it gains roster reading and live `opencode` and `copilot` backends.

### 4.6 Rule 8 — Harness discipline (G6)

`templates/discipline.md` is copied to `.harness/discipline.md` at scaffold and read by lead, builder, reviewer, verifier. Enforcement, not just text:

| Rule | Where it bites |
|---|---|
| Define done first | Plan checkpoint will not open without a Done section: outcome plus check method (tests, visual, source, review). Lead refuses to plan without it. |
| End with a receipt | `templates/receipt.md`: tests run with pass/fail counts, review verdict, approver, steps outside the change, open risks, rollback point. Shown at the ship checkpoint and appended to the PR body. |
| Cap fix rounds at three | Already in `run` (line 43) and per-lane (line 28); wording changed to "stop and escalate with what failed" and the escalation goes into `state.md`. |
| Repeat mistake → check | `learn` detects a lesson seen twice (same normalized text or same file+rule) and offers to promote it: a `stop-checks.sh` rule, a test skeleton in the repo's test dir, or a line in `review-checklist.md`. Records "lives at <path>" in `lessons.md`. |
| State outside the chat | `.harness/state.md`: decisions, failures, open items, appended by run and learn; read at session start by `session-lessons.sh`. Notion sync is out of scope; the file is the record. |
| Auto-add the receipt | New hook `hooks/pr-receipt.sh` on `PostToolUse` matching `gh pr create|gh pr edit`: if the PR body lacks `## Change receipt`, edit it in. If neither `.github/pull_request_template.md` nor the `Dobeu-tech-eco/.github` org default contains the receipt section, add or extend the template in the same branch without asking. Org-default detection: `gh api repos/Dobeu-tech-eco/.github/contents/.github/pull_request_template.md`, cached per session. |

### 4.7 Review: security, critique, walkthrough (G7)

The reviewer agent gets three new axes selectable by the lead based on the diff:
- **security** — dependency audit (`npm audit`, `pip-audit` when present), secret scan of the diff, OWASP-shaped checklist. Findings use Issue / Impact / Evidence / Fix / Priority.
- **critique** — UX design review modeled on Impeccable's structure: design quality, usability checks scored 0–4 with n/a excluded, two simulated-user walkthroughs framed as hypotheses, and a Priorities block split preserve / fix / open questions. Never edits. Report saved to `.harness/review/critique-<stamp>.md` (tracked). If Bakaus's Impeccable is installed (`/impeccable critique` available), the axis calls it and files its report instead of running its own.
- **walkthrough** — the verifier (not a new agent) drives the app screen by screen: Playwright in the workspace when a dev server is configured in `config.yaml`, else Claude in Chrome or the built-in browser when present. One screenshot per screen to `.harness/review/screens/` (ignored), one line per screen in the verify report: expected, observed, pass/fail. Walkthrough runs only when `end-state.md` names UI components.

The lead's selection rule (my call): security always on for diffs touching auth, network, deps, or env; critique and walkthrough on when the diff touches UI components named in `end-state.md`.

### 4.8 `gtm` skill — go-to-market one pass (G8)

`skills/gtm/SKILL.md` orchestrates, in order, the installed `marketing-skills` plugin: `product-marketing-context` (auto-draft from repo) → `competitor-profiling` → `seo-audit` → `page-cro` → `copywriting` then `copy-editing` → `launch-strategy` → `analytics-tracking` (optional). Each step reads `.agents/product-marketing-context.md`. Output: `.harness/gtm/<stamp>/` with one report per step and a `readiness.md` scorecard (what is ready, what blocks launch, who owns each item). The harness feeds each step what it already knows: topology and acceptance criteria from `end-state.md`, the marketing surface list from scout.

Preflight: if `marketing-skills` is not enabled, say so and print the install path (it is a claude.ai synced plugin for Jeremy; on other machines, the marketplace install line). No fallback re-implementation.

### 4.9 Other harnesses in the repo

Scout detects foreign harness state: `.omc/` (oh-my-claudecode), `.flow/` (flow-next), `.beads/`, `.conductor/`, `.agent/`, `.impeccable/`, `.agents/` (marketingskills context), and any `AGENTS.md`/`CLAUDE.md`. The interview's brownfield step asks once per harness found:

- **import** — read its specs, plans, and state as inputs to `end-state.md` (an `.omc/specs/deep-interview-*.md` maps almost field-for-field; `.flow/` plans map to components). The source stays untouched.
- **coexist** — leave it alone. The lead and builders may read it, never write to it. `ensure-ignored.py` does not touch its paths.
- **retire** — move it to `.harness.bak-<stamp>/<name>` after import; offered only when the user says the other harness is no longer in use.

Default when the user doesn't answer: coexist. `run` records the decision in `state.md` and never asks again unless a new foreign folder appears. `CLAUDE.md` and `AGENTS.md` are always read and never rewritten by the harness; conflicts between them and `discipline.md` are surfaced at the plan checkpoint, and the repo file wins.

### 4.11 Decisions from the builder check

0. **2026-10-21 additions from Jeremy:** agents round in onboarding (Claude-only is fine), repos round before the interview with per-repo purpose, `learn` auto-runs after ship unless `auto_learn: false`.
 (my calls unless marked)

1. **Existing v2 repos keep working.** `run` in a repo with `.harness/config.yaml` but no `end-state.md` runs as today and prints one line: "No end state yet; `/dts2-harness:setup` interviews to one." `setup --scaffold-only` skips the interview. Batch mode stays scaffold-only; the interview is per repo, on demand.
2. **PR receipt hook pushes.** A PR exists only because its branch was already pushed, so the hook commits the template on that branch and pushes that branch only. It acts on every `gh pr create`/`gh pr edit` while the plugin is enabled, per Rule 8.6 ("whenever a bot works on a PR"). This is a deliberate, narrow exception to "never push without a yes" and is written into `discipline.md`. Decided 2026-10-21.
3. **Critique reviews screens.** The walkthrough runs first; the critique axis consumes its screenshots and the diff. Review phase becomes: verifier walkthrough → reviewers (all axes) in parallel. Without a browser, critique falls back to source-only and says so.
4. **Lessons promote to a repo-local check file.** `.harness/checks.sh` is sourced by `stop-checks.sh` if present. `learn` writes there; the plugin hook is never edited by `learn` (that is `evolve`).
5. **Workspace end state is layered.** One `end-state.md` per repo plus `end-state.md` in the workspace root for cross-repo components. `run` reads the repo file and the workspace file's rows that name this repo. Clarity is scored by `scripts/clarity-score.py` from a ratings JSON the lead emits each round, so the score is deterministic and testable.
6. **Headless runs are live-agents-only.** If the roster assigns a lane to a handoff agent, `dts2-run.py` exits 2 with "handoff lane needs a person" unless `--live-only` reassigns those lanes to Claude.
7. **Harness dependencies survive pruning.** `plugin.json` keywords plus `profiles/blueprint.json` → `requiredByHarness: ["marketing-skills@synced", "impeccable@*"]`. Every machine-prep tier keeps these and says why.

## 5. What is left to the builder

- Exact clarity-score weights (start from 40/30/30, brownfield 35/25/25/15, tune on two real repos).
- Transcript parsing details for `usage-scan.py` and its tolerance for schema drift across Claude Code versions.
- Agent-set hashing for redundancy (name list vs content hash; name list is probably enough).
- Playwright vs browser-tool selection order and what to do when neither exists (report "walkthrough skipped: no browser").
- Cursor and Antigravity native rules-file formats; verify against current docs before writing templates.
- Test plan: fake-home fixtures for machine-prep tiers; a sample repo for setup→run→receipt; a clean-install check from GitHub as in 2.1/2.2.

## 6. Acceptance

- In a fresh clone of a single repo: `setup` ends with `end-state.md` at ≥80% clarity, `run` on one slice reaches the ship checkpoint with a receipt, and the words "worktree" and "lane" never appear in output.
- `machine-prep --tier standard` on the WSL/Windows machine reports usage counts, lists the seven redundant agent packs, and the plan is idempotent.
- `evolve` changes a skill, validates, bumps, and prints the update commands without touching the install cache.
- `gh pr create` from a harness run yields a PR body with a Change receipt, and a repo without a PR template gets one in the same PR.
- `claude plugin validate` passes for the plugin and the marketplace; clean install from GitHub loads 8 skills and 6 agents.
