# dts2-harness v3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship dts2-harness 3.0.0 to the public marketplace with end-state onboarding, three machine-prep tiers, named checkpoints, an agent roster, enforced harness discipline, critique/security/walkthrough review, a GTM pass, and an `evolve` skill.

**Architecture:** Everything lives under `plugins/dts2-harness/`. Behavior that must be deterministic (scores, usage counts, ignore rules, redundancy) is Python stdlib in `scripts/` with unittest coverage in `tests/`. Behavior that is agent judgment lives in `skills/*/SKILL.md` and `agents/*.md`, pinned by a text-contract test that asserts required phrases are present and forbidden phrases absent. Hooks are POSIX bash.

**Tech Stack:** Python 3.10+ stdlib (`json`, `pathlib`, `hashlib`, `argparse`, `unittest`), bash, Claude Code plugin manifest, `claude plugin validate`, `gh` CLI.

**Spec:** `docs/superpowers/specs/2026-10-21-dts2-v3-design.md`

## Global Constraints

- Plugin name `dts2-harness`, marketplace `dts2`; version `3.0.0` in both `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`.
- Exactly 6 agents: lead, builder, reviewer, verifier, scout, auditor. No new agent files.
- Exactly 8 skills: onboard, machine-prep, setup, run, learn, sdk, evolve, gtm.
- Kebab-case names; no "claude" or "anthropic" in skill or plugin names; all intra-plugin paths use `${CLAUDE_PLUGIN_ROOT}`.
- Scripts: Python stdlib only; explicit type annotations; named constants (`Final`); functions under ~20 lines; early returns.
- Never read credential files; never write keys; `.claude.json` and `auth.json` are out of bounds.
- Single-repo user-facing text in `run` never contains the words "worktree" or "lane".
- Review never edits. Only the ship checkpoint's explicit yes commits. The only push the plugin ever performs is `pr-receipt.sh` on the PR's own branch.
- Clarity threshold default `80`; only the literal reply `Continue anyway` passes early.
- Upstream attribution in README → Acknowledgements: oh-my-claudecode (MIT), Impeccable (Apache-2.0), marketingskills (MIT).
- Run all tests with `python3 -m unittest discover -s plugins/dts2-harness/tests -v` from the repo root.

## Review Focus

1. A repo with v2 `.harness/config.yaml` and no `end-state.md`: `run` must work and print the one-line nudge, not refuse. (Task 9 text test.)
2. `machine-prep --tier strict` on a home where `marketing-skills@synced` is the only synced plugin: it must stay enabled with reason `requiredByHarness`. (Task 2 test.)
3. Session transcript JSONL with unknown record shapes or malformed lines: `usage-scan.py` must skip them, not crash. (Task 1 test.)
4. `pr-receipt.sh` when `gh` is missing or the PR body already has `## Change receipt`: no edit, exit 0. (Task 4 test.)
5. `ensure-ignored.py` run twice, and run on a repo whose `.gitignore` lacks a trailing newline: idempotent, no duplicated lines, no joined lines. (Task 1 test.)
