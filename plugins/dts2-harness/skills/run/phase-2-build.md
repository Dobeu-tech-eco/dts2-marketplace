# run — Phase 2, build

## Phase 2 — Build (parallel builders)
0. **Wave 0 (Foundation).** The plan's `## Foundation` section runs before anything else: dispatch only that section's builder (model and effort as in step 2), wait for it to report done, run the **Audit before merge** below, merge it, and only then release the rest of the plan and the `## Ready queue` to steps 1 onward. `Foundation: none needed` skips wave 0. Wave-0 files are not part of any later builder's file set.
1. Builders = min(builder sections in the plan, scout's builder count, `max_builders`). Each builder works on its own file set in the isolation that **Isolation (Rule 10)** below sets.
2. Every dispatch names a model AND an effort (Rule 9.2). Resolve both with `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/delegate.py" --agent <name> --seat execution --complexity <c>`: mechanical → economy/low, normal → standard/medium, design → standard/high. A builder NEVER runs a frontier model; harder sections raise effort, not tier. A Claude builder is an Agent dispatch with that `model`, run at that effort. A live non-Claude builder runs through Bash. Write its brief to `.harness/runs/<stamp>/prompts/builder-<n>.md` (any diff it needs goes in a file beside it, named in the brief), then run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/roster.py" command --agent <name> --role builder --tier <the resolved tier> --effort <the resolved effort> --prompt-file <file>` from the target repo and run its `shell` value as is. That line is already quoted: it passes the file through `--prompt-file` where the CLI has one (grok, muse) and otherwise a fixed pointer to the file (agy also gets the file's folder as `--add-dir`); it carries the profile `env` as an `env K=V` prefix (grok: `env GROK_WORKFLOWS=0`, since `--no-subagents` does not stop background workflows), the resolved model, the stdin redirect and the permission flags the profile needs (grok builders: edits allowed, no shell, no subagents or MCP, edits only inside the working directory and never under `.git`, `.grok`, `.claude` or `.cursor`; grok reviewers: no edits, shell, subagents or MCP). Never paste the brief or the diff into a command line: that invites shell injection and breaks on long diffs (E2BIG). Follow the `notes` it returns. The `shell` line already redirects stdin when the profile sets one (codex: `< /dev/null`, or it hangs waiting on stdin). Codex cannot write the git index from its sandbox: tell every codex builder `do not commit`, and the lead commits its work after review. Save every live non-Claude dispatch's combined output (`2>&1`) and exit status, then pipe the output to `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/roster.py" classify --agent <name> --role <role> --exit-code <status>`. It reads only the last 20 lines and counts an error only at column 0, optionally after one status marker (`!`, `✗`, `×`, `Error:`, `fatal:`), never after a list or quote marker, so a review that quotes an error string is never misread. Marker lines count only after a non-zero exit; the recorded muse forms (`agent loop failed: model failed: API error 402 …`, `API error 429 …` at line start) count at any exit, because muse's exit code on them is unrecorded. `dropForRun: true` (a 402 billing or 429 quota answer, `unavailable (billing/quota)`) drops that agent for the rest of the run: print `Dropped: <agent> — <reason>` with the reset time when given, and give the seat to the next usable agent. It is not a failed round and never fails the builder or the run. Any other non-zero exit comes back as `outcome: failed` with `seatFailed: true`: that is a failed round under the fix loop, never finished work.
   **Finalization before tests.** Put this order in every builder brief: implement the section against its done-criteria; when the implementation is complete and BEFORE writing any tests, ask `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/companion-gate.py" check --repo . --skill improve-codebase-architecture` (run from the builder's checkout, so uncommitted work is measured); on `run: false` skip the pass and the manual fallback and go straight to the tests, otherwise run `npx skills add https://github.com/mattpocock/skills --skill improve-codebase-architecture` (see Companion skills in `.harness/discipline.md`) scoped to the builder's file set for a refactor plan on the just-written implementation, apply the worthwhile simplifications inside the file set; THEN write the tests. If the skill cannot install or run, the builder does a manual scoped simplification pass instead (duplication, dead code, unclear names, speculative abstraction) and says so in its report. This inserts between implementation-complete and tests; define-done-first (Rule 8.1) is unchanged.
3. Dispatch every independent builder in one message so they run at once, each with the model and effort from step 2. Dependent builders start only after their dependencies report done.
4. **Handoff agents** (in the roster's `handoff` list): write `.harness/handoff/<agent>/<n>.md` (the builder's tasks, files, done-when) and the agent's rules file from its profile `rulesFile`, then pause that builder until the user says done. Record it with `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/action-items.py" <repo> add Handoff ".harness/handoff/<agent>/<n>.md builder <n>"` and `… assign <id> <agent>`; mark it `done` when the user reports done.
5. A builder that asks for a file outside its file set: pause that builder and ask the user.
   **Database builders.** dts2-harness:builder has no MCP tools, so a database builder brief routes it through the Supabase CLI on a disposable branch: `supabase branches create`, `supabase db query --linked --project-ref <branch_ref> -f <file>`, `supabase branches delete`. Say in the brief that the CLI resolves `-f` paths from the project root and prints an `Initialising login role` line before its JSON, and never `supabase branches get`, which prints keys.
6. Every builder report ends with a `FLAGS:` block. On each report run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/flags_collect.py" --repo . --stamp <stamp> --builder <n> --report-file <the saved report>` (or pipe the report on stdin): it appends the flags to `.harness/runs/<stamp>/flags.md`, and a report with no block is recorded as `MISSING`. A builder that reports `SECRET NEEDED`: handle it as in **Secrets** below; the others keep going.
7. A builder failing on the same error: At fix round 2 on the same failure (the first fix did not clear it), install and run `/diagnosing-bugs` (see Companion skills in `.harness/discipline.md`) on the failing test or finding BEFORE dispatching the second fix (same model and effort as the first dispatch); paste its root-cause output into the round-2 builder brief and write its summary line to `.harness/state.md` under `## Failures and escalations` next to the round record. Round 3 and the cap are unchanged. Rounds 1–2 resume the same builder; round 3 goes to a fresh builder one tier up (`economy→standard`, or one effort level higher when already on standard; never frontier); after round 3 stop it, escalate with what failed, and record it in `.harness/state.md` under `## Failures and escalations`. At the hard round-3 cap with bugs still failing, first auto-run a fresh `/diagnosing-bugs` pass (`npx skills add https://github.com/mattpocock/skills --skill diagnosing-bugs`) on everything still failing (upstream renamed `diagnose` to `diagnosing-bugs`, so the hard cap reruns that skill from scratch, not the round-2 output), apply its findings, and only then escalate to the user with what still fails. Three materially identical failures mean change the approach, not retry blindly.
8. Run the integration task, if any, last. Show `git diff --stat` per repo.

**Mechanical dispatches (AA-8).** No new agent: every section rated `complexity: mechanical`, and the phase-4 release notes and PR body drafting, dispatch `dts2-harness:builder` with `model: haiku, effort: low`; the lead still audits the result like any builder's.

**Audit before merge (G-24, AA-1).** When a builder reports DONE, before merging or marking its section `done`, run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/builder-audit.py" --repo <its checkout> --base <the commit it started from> --owned <its file set, comma-separated> --claimed-sha <the commit it reported> --status DONE --attempt <re-dispatches so far>`. Exit 1 means one of: an empty diff with DONE, a changed file outside its owned set, or a claimed commit that is not HEAD. Read `action` in the JSON: `redispatch` → re-dispatch once to the same builder (same model and effort) with the violations pasted into the brief; `blocked` (the second failure) → park the section as `blocked` with an action item, never merge it.

### Secrets
A secret's value never passes through the chat, a prompt, or an agent's context. On a builder's `SECRET NEEDED: NAME — <what it unlocks> — <where consumed>` line, pause that builder only and ask once: **provide now** or **add later**.
- **provide now**: name the variable and exactly one place to put it: a `NAME=` line in `.env`, the project's secret manager command, or `gh secret set NAME` for CI. Wait for the user to say "done". Check presence only, never print a value: for `.env` or the environment, `test -n "${NAME:-}"` or `grep -qE '^NAME=.+' .env`; for GitHub Actions (`gh secret set NAME`), `gh secret list | grep -qE '^NAME\b'` (key names only). Present → resume the builder. Missing → say so and ask again once.
- **add later**: append `| NAME | <what it unlocks> | <where consumed> | <how to add> | open | | <YYYY-MM-DD> |` to `.harness/action-items.md` → `## Secrets` (create from the template if absent); add `NAME=` with a one-line comment to `.env.example`; let the builder keep its not-configured path. If any wiring was left undone because the secret is missing, write the status as `open, deferred wiring` and say what was deferred in `consumed in`.

The run continues either way. Open secrets appear in the receipt under *Steps outside this change*, and they never block the commit or the PR.

## Continuous dispatch (never idle)
Setting: `continuous_dispatch: true` (default) and `builder_timeout_min: 20` in `.claude/dts2-harness.local.md`. With `false`, Phase 2 dispatches the plan once and waits, as before.

Keep `max_builders` (from the tier) builders in flight at all times while the lead's `## Ready queue` is non-empty. On any builder event (finished, reported BLOCKED or NEEDS_CONTEXT, `SECRET NEEDED`, no report within `builder_timeout_min`, entering fix round 2 on the same failure, or entering fix round 3) do two things in one step:
- (a) **Handle that builder.** VERIFIED-ready: merge its branch. Stalled: park its section as `blocked` with an action item (Secrets, Decisions or Handoff), write the id into the section cell in `end-state.md` (for example `payments webhook (S2)`), and clean up its builder checkout as **Isolation (Rule 10)** says. At fix round 2 on the same failure run `/diagnosing-bugs` before the second fix and paste its root cause into the brief. If the fix-round cap is hit, run a fresh `/diagnosing-bugs` pass if bugs are still failing, then escalate per Rule 8.
- (b) **Dispatch the next ready section(s)** from the queue to fresh builders in the same message, each with the model and effort resolved as in step 2. Re-check that each file set does not overlap any in-flight builder; on a conflict skip to the next ready section. If every ready section conflicts, wait for the next event instead of dispatching.

When a builder-branch merge conflicts, install (`npx skills add warpdotdev/common-skills@resolve-merge-conflicts -a claude-code --copy -y` if the pre-check could not) and run `/resolve-merge-conflicts` before touching the conflict by hand (see Isolation (Rule 10)); if it cannot resolve cleanly, stop and hand it to the user.

Stuck-but-not-stopped: a parked section never halts the run. The run ends only when the queue is empty and no builder is in flight, at a checkpoint, or on a hard stop or context guard.

Partial ship: at the ship checkpoint, verified sections ship; parked sections are listed in the receipt under `Steps outside this change` with their action-item ids, and the section statuses in `end-state.md` are updated (`done`, `blocked` or `todo`).
