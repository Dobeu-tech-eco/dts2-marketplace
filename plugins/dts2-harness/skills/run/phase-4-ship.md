# run — Phase 4, ship

## Phase 4 — Ship checkpoint
1. Merge findings, dedupe by file:line, keep the highest severity.
2. Build the receipt from `${CLAUDE_PLUGIN_ROOT}/templates/receipt.md` and save it to `.harness/runs/<stamp>/receipt.md`: tests run with pass/fail/skip counts from the verifier, review verdict, approver (left as the template placeholder until ship), steps outside this change (open secrets and decisions from `.harness/action-items.md`, handoff work), open risks, rollback point (the SHA recorded in preflight).
   **Delegation.** Fill the receipt's `### Delegation` section: a `Models:` list with one line per builder, `<agent> <model> tier=<tier> effort=<e> (execution)`, and one per advisory or sign-off seat, `<agent> <model> tier=<tier> effort=<e> (advisory)` or `(signoff)`. `scripts/delegate.py` `receipt_line` builds that row. An observed model id maps to the profile tier that names it; an unpinned codex run (no `-m`, the config.toml default gpt-6.1-sol) is `tier=standard`. Then `Delegation policy: OK`, or `Delegation policy: VIOLATION: <builder> ran frontier` when `violates_execution_policy` (in `scripts/delegate.py`) is true for any builder. The final review raises a violation as a ship-blocking finding.
3. Show the receipt, findings by severity, the verifier verdict, and lesson candidates. Then say exactly: "Here is the receipt. Ship, fix the blocking items and re-check, or stop and revert."
- **Fix**: send only the CRITICAL and HIGH findings to the builders that own those files, then rerun Phase 3. At fix round 2 on the same failure (the first fix did not clear it), install and run `/diagnosing-bugs` (see Companion skills in `.harness/discipline.md`) on the failing test or finding BEFORE dispatching the second fix; paste its root-cause output into the round-2 builder brief and write its summary line to `.harness/state.md` under `## Failures and escalations` next to the round record. Cap at 3 rounds. After 3, stop and escalate with what failed; record it in `.harness/state.md`. When the hard round-3 cap is reached and the rerun still has failing bugs, first auto-run a fresh `/diagnosing-bugs` pass (run `/diagnosing-bugs` per Companion skills in `SKILL.md`) on everything still failing (upstream renamed `diagnose` to `diagnosing-bugs`, so the hard cap reruns that skill from scratch, not the round-2 output) (see Companion skills in `.harness/discipline.md`), apply its findings, and only then escalate to the user with what still fails. Rounds 1–2 resume the same builder; round 3 goes to a fresh builder one tier up (`economy→standard`, or one effort level higher when already on standard; never frontier).
- **Ship**: fill the receipt's `### Approved by` line with `$(git config user.name), $(date +%Y-%m-%d)` (ISO date), replacing the template placeholder; never create a PR from a receipt that still has it. Then do **After ship** below, then propose one commit message per repo. As the last gate before `git commit`, follow **Companion gates** below: only when its check answers `run: true`, install and run `npx skills add https://github.com/mattpocock/skills --skill setup-pre-commit` (see Companion skills in `.harness/discipline.md`) so the repo's pre-commit hooks are in place, and right after that pass succeeds run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/companion-gate.py" record --repo . --skill setup-pre-commit` as its own step, before the commit; commit only on an explicit yes. Never push. When the user pushes and asks for a PR, first install and run `/pr` to produce the PR title and body, append the receipt's Change receipt section to that body (the hook still guarantees it), say `PR body written by /pr; receipt appended.`, then create it with `gh pr create --body-file <that body file>`; open secrets do not block it. The same applies before `gh pr edit --body-file`. Install with `npx skills add https://github.com/mattpocock/skills --skill <name>` on first use (see Companion skills in `.harness/discipline.md`), record it in `.harness/keep.yaml` → `skills:` as `- name: <name>` / `source: npx skills add https://github.com/mattpocock/skills --skill <name>` / `serves: harness`, invoke by slash name with the Skill tool (or read its SKILL.md inline when headless); if `npx` is unavailable or the install fails, print `Skill <name> not installed (npx unavailable or offline); continuing without it.`, add a Decisions action item with the command, and continue.
- **Stop and revert**: revert the run's changes the way the user picks, restore any stash, and clean up the run's builder checkouts as **Isolation (Rule 10)** says.

**Companion gates.** The answer from `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/companion-gate.py" check --repo . --skill setup-pre-commit` governs the pre-commit companion: `run: false` means the repo already had that pass, so skip it. On `run: true`, run the companion, then the `record` step above, so later runs skip it. The architecture pass is gated where it runs, in Phase 2 finalization, not here.

Verifier BLOCKED means not done, unless the user explicitly overrides; the reason then goes in the commit message and `.harness/state.md`.

## After ship
Do these before the commit so they land in it. Do not narrate the writes.
1. Append the reviewers' lesson candidates to `.harness/lessons-inbox.md`. If `auto_learn` is not `false`, run the `learn` skill in its auto mode on those candidates and put the resulting `lessons.md` diff in the ship summary; no separate approval prompt. If `auto_learn` is `false`, still run only learn's **Run metrics** step so the Trend line stays current.
2. In `.harness/end-state.md`, check the acceptance boxes the plan covered and the verifier confirmed, and update each touched component's status.
3. Append the ship decision to `.harness/state.md` → `## Decisions` as `- <date> <what shipped, receipt path>`.
4. **Write handoff.** Run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/handoff-write.py" <repo>` last, after the other writes, so `.harness/handoff/latest.md` reflects them. It never contains a secret's value.
5. Include `lessons.md`, `.harness/metrics.jsonl`, `.harness/harness-lessons.md` (if changed), `end-state.md`, `state.md`, `action-items.md` (if changed), and `.harness/review/critique-<stamp>.md` (if written) in the commit. `handoff/latest.md` is regenerated, not committed.
6. **Harness sweep (evolve).** After the commit is proposed (so the plugin change never mixes into the repo's commit), if `.harness/harness-lessons.md` has open lessons, run `/dts2-harness:evolve` in its **Harness lessons** mode automatically: it quotes each open lesson, proposes the plugin edit in the dts2-marketplace source, and changes nothing without an explicit yes per lesson; it pushes only on a further explicit yes. The user never has to remember to call evolve. Skipped in headless runs (lessons stay open for the next interactive checkpoint).

## Deployment verification
Runs only when `deploy.provider != none` in `.harness/end-state.md`. Read `deploy.provider`, `deploy.productionUrl`, `deploy.checkCommand` and `deploy.status`. The harness never deploys, pushes, or re-runs CI except on an explicit yes inside the troubleshoot round below. It never creates provider accounts or enters credentials; secrets are presence-only.

If the `deploy:` block is missing or `provider: unset` (v2 or `--scaffold-only` repos), after the PR is opened run `deploy-detect.py` and ask the setup skill's deploy question once, record the answer in `end-state.md`, then continue.

**Planned deploy.** Started from Preflight step 4. When `deploy.status` is `planned`, build `deploy.plan` as its own run, before any feature run: the provider config file, a deploy workflow, secret names to `## Secrets` (never values) and DNS, domain and account steps to `## Deploy` in `.harness/action-items.md`, via `action-items.py <repo> add`. On the first passing deploy, set `deploy.status` to `live` and run the production walkthrough below.

**Watch.** After the PR is opened, print: `Deploy watch: <provider> — run `<checkCommand>` or tell me when it is live`; when `checkCommand` is null, print `Deploy watch: <provider> — tell me when it is live`. Wait for the user to confirm, or for the check output they paste to show the new commit deployed. Never run the deploy yourself.

**Production walkthrough.** Once confirmed, dispatch `dts2-harness:verifier` (the `model` override is the claude frontier tier from `roster.py model --agent claude --tier frontier`) with `Mode: production`, `URL: <productionUrl>`, the plan's `Done` screens and the run stamp. It repeats the walkthrough screens against the URL, saves `prod-<screen>.png`, and returns PASS or FAIL per screen. Replace the line under the receipt's `### Production` heading with `- Production: <url> | <deploy id or commit> | walkthrough PASS n/n | <ISO time>`, then update the open PR with `gh pr edit <n> --body-file .harness/runs/<stamp>/receipt.md`.

**Walkthrough fallback.** When the verifier has no browser tool (no Claude in Chrome, no built-in browser, no Playwright of its own), the lead runs `python3 scripts/walkthrough_fallback.py --out .harness/runs/<stamp>/prod-shots --url <productionUrl>/<screen> ...` instead. It works only with the sandbox on, only against `walkthrough: allowed_hosts:` in `.harness/config.yaml`, refuses `file://` and every non-http(s) URL, aborts page requests to other hosts, and prints a `report` section with a screenshot per screen to paste under the receipt's `### Production` heading. Without Playwright it reports `skipped`; record that in Open risks, never as PASS.

**Vercel verified commits.** A Vercel preview marked `Canceled` because the project requires verified or signed commits is non-blocking when the commit is one of the run's unsigned agent commits: record it as a note, not a failure, in the receipt's Open risks (`Vercel preview canceled: unsigned agent commit`), and do not start the troubleshoot round for it. The production walkthrough runs only after a signed or human commit that contains the agent's changes deploys (`git merge-base --is-ancestor <agent sha> <deployed sha>`); record that deployed commit in the receipt before the walkthrough.

**Failure.** A FAIL in the deploy check, CI, or the walkthrough → ask exactly: "Production/CI failed at <step>. Investigate and troubleshoot?"
- **No**: record an open item in the receipt (`Production:` line and Open risks) and in `.harness/state.md`, and end the run.
- **Yes**: troubleshoot round. Gather evidence (`gh run view <id> --log-failed`, provider logs, the walkthrough's console and network errors), state the root cause, propose a fix, then present these options, each needing its own explicit yes:
  - (a) follow-up PR (default)
  - (b) `gh run rerun <id>`
  - (c) redeploy or push to production with the provider command from `DEPLOY_COMMANDS` in `deploy-detect.py`: vercel `vercel --prod`, cloudflare `wrangler deploy`, netlify `netlify deploy --prod`, fly `fly deploy`, github-workflow `gh workflow run <file>`
  - (d) roll back to the receipt's rollback point

The troubleshoot round counts toward the 3-round cap. Without that explicit yes the harness never deploys, pushes, or re-runs CI.
