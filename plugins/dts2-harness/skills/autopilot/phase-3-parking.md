# autopilot - sections 4 and 5a, parking, hard stops, resume and adjudication

## 4. Parking, hard stops, and resume
- **Park** (the step stops, the run continues with steps that do not depend on it): fix-round cap reached, merge refused, a dependency parked, a handoff-only builder, a voter-pool collapse for that step, or a council that could not seat five valid ballots, produce a valid decision record, or confirm its changes. A pre-check that reports a skill gone upstream never swaps under autopilot: it becomes a Decisions action item listing the ranked candidates, for the user to approve later. Each park gets an action item (Secrets, Decisions or Handoff), its id in the table's status and in the section cell (`payments webhook (D4)`).
- **User-input items never park.** A missing value the user must supply never slows or stops a task: the builder wires it by name, tests mock it, and the item is filed with `action-items.py add <group> "<title>" --task <onboard task id>` so its row reads `TASK_<task>_<item id>-<title>` (`TASK_A1_S2-stripe secret`). `action-items.py done <id>` prints the linked task so the resume knows which PR it unblocks. The task builds, votes and opens its PR as normal; what it cannot do is merge (section 5a).
- **Hard stop** (the whole autopilot stops, handoff written, `.harness/autopilot/latest.md` status `stopped`): the context guard fires; a change would touch a `do_not_touch` path; a step would deploy to production (other than a default-branch merge the step-5 confirmation approved by name), delete data, force-push, rewrite published history, or push to `main`/`dev` directly; a pre-check upgrade; the user interrupts.
- `autopilot resume` reads `.harness/autopilot/latest.md` and continues at the first step that is not `done` or `parked`, re-running the pre-check first.

## 5a. Adjudication
Every run, `autopilot` or `fullauto`, ends the same way: before the final report, present every open user-input item to the user together, grouped by the PR it blocks, not one at a time as they were filed.
- A PR whose completion needs a value the user has not supplied (a database to create, a secret to use or share, a paid side effect) stays at `pr-open`: it is never merged and its section is never `done` while an item on it is open. Its body carries `## Blocked by` listing the `TASK_` items; the lane is marked with `lanes.py heartbeat <stamp> --lane <lane> --status blocked --reason awaiting-items --blocked-by <item ids, comma separated>`.
- Keep the open PRs at the end to as few as the feasibility test allows: bundle blocked tasks of the same section onto one PR (section 2 step 6, no file overlap, at most `MAX_BUNDLE`) rather than one PR per task, and before the ledger is written fold non-conflicting blocked lanes into one PR. Never split a blocked PR to make the ledger look shorter; a long list of tasks on one open PR beats many open PRs.
- Write and print the task ledger: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/task-ledger.py" <stamp>` produces `.harness/runs/<stamp>/task-ledger.md`, one row per open PR (number, branch, bundled tasks, blocking item ids and titles) and the count line `N open PRs, M blocking items`. Link it from `.harness/state.md` and the final report.
- When the user marks an item done, the next run or `resume` runs `task-ledger.py <stamp> --resolved` first; every PR it lists (all of its items done) is rebased on the fetched base, re-verified, and merged through section 3 and its post-merge check, and its row becomes `merged`.
- `fullauto` stops only when nothing is outstanding and every lane is `done`, or `blocked` with its items in the ledger.
