# autopilot - section 0, pre-check and preflight

## 0. Pre-check and preflight
1. Run the run skill's **Pre-check (every run command)**. An upgrade it starts stops autopilot; the handoff records `Next action: /dt:autopilot resume`.
2. Open the typed run record: `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py" run-record <stamp> --init --kind autopilot` (a dpp son's record already exists; skip it there). Then run the run skill's Preflight steps 0–7 (scope, harness-change guard, config, ignore guard, end state, settings, roster, clean tree). Skip its loop-me check-in and the step-8 clarifying question: autopilot asks nothing mid-run.
3. **Resolve the steps** into an ordered queue: sections by their `depends on` order (a listed section whose dependency is neither `done` nor in the queue → park it, see section 4); action items in the order given; a `feature` step runs the feature skill first and its new sections join the queue right after it.
4. **Base and merge target.** `<base>` is `dev` when it exists on the remote. With no `dev`, the base is the default branch, and a merge there is usually a production deploy (Vercel, Lovable, Netlify and similar deploy the default branch). In that case autopilot merges only if the upfront confirmation below names the default branch explicitly and the user says yes; otherwise every step stops at `pr-open` (consensus passed, CI green, PR left for the user), and any later step that depends on it is parked until that PR is merged. On a yes, record it at once with `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py" merge-target <stamp> --set <default branch> --yes-default-branch`; the merge guard blocks the default branch unless a grant names the PR head, and `merge-go-step` (section 3 step 4) refuses to write one for the default branch without that record.
5. **One upfront confirmation, then none.** If any step touches production deploys, data deletion, auth, or payments (the run skill's Preflight step 9), or the merge target is the default branch, list those steps (and `merges go to <default branch>, which deploys production`) and ask once: `Autopilot will plan, build, merge and continue through these without asking again. Go? (y/n)`. None of these → no question. After this point autopilot never waits for the user unless a hard stop below fires.
6. **Voters.** One seat per provider: claude (Opus) always holds the first, then the first two other providers in the probe's `usable` list whose frontier model is set (`roster.py model --agent <name> --tier frontier` is not `null`; for example codex `gpt-6-astra`, gemini, grok, muse), in roster order. An agent with budget `low` is still eligible, since a vote is a `second-opinion` seat. These three are the **panel**. The **council** (section 1b) is five seats spread across as many different frontier providers as possible: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" seats --usable <probe usable, comma-separated>` gives one seat to each usable provider with a frontier model first (claude, codex, gemini, grok, cursor, muse, in that order), and only when there are fewer than five providers does a provider take a second seat, always with a different model (for example Claude Opus 5.5 and Claude Fable 5.0), so no two seats are the same model. A `council:` block in `.harness/config.yaml` changes the defaults: `order: [...]`, `exclude: [...]`, and `models: [provider:model, ...]` for extra frontier models a provider may field (needed for cursor, which has no default frontier model). When `seats` returns a non-empty `stale` list (provider names), print one warning line per provider with its `checked` date from the matching `freshness` entry (`Council model list for <provider> last checked <date> (none recorded when null); refresh its councilModels.`); it never blocks the council. A **council** seat is dispatched only with `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/ballot_dispatch.py" dispatch --seat <seat> --model <model> --prompt-file <ballot> --out-dir .harness/runs/<stamp>/council/<step>` (add `--provider <name> -- <argv>` for a non-Claude seat): it writes the ballot and its `<ballot>.dispatch.json` provenance record, and `council.py tally` does not count a ballot without it. Panel voters are dispatched as follows; each seat says how: `agent-tool` (`dt:reviewer` with that `model`), `claude-cli` (`lanes.py call <stamp> --label <seat> --out <file> --prompt-file <ballot> -- claude -p --model <model> --output-format json`; the ballot is piped to the seat's stdin, and the seat shares the global call limit, backoff and spend counter), or `roster-command` (get the argv with `roster.py command --agent <provider> --role second-opinion --tier frontier --model <model> --prompt-file <ballot>`, then run it only as `lanes.py call <stamp> --label <seat> --cost-source none --out <file> --prompt-file <the output's stdin path, when it has one> -- <env pairs and argv from that output>`; a non-Claude CLI never prints a cost, so `--cost-source none` counts the call without treating its spend as unknown). An `agent-tool` seat cannot be gated this way and is outside the call limit and spend counter. A seat whose dispatch fails or is classified unavailable is replaced by the first `bench` seat; rerun `seats` with `--failed <provider:model,...>` if the bench is empty. `ok: false` (fewer than five distinct provider/model seats) → the council cannot sit and the step parks. Claude Fable 5.1 is the **head of council** and never holds a council seat. Claude Fable 5.1 is also the **tiebreaker**: dispatched directly with the Agent tool, `subagent_type: dt:reviewer`, `model: fable`; it never sits on the panel. Fewer than three usable frontier providers → say `Autopilot needs 3 frontier providers; only <n> usable (<names>). Falling back to the normal human checkpoints.` and run `/dt:run` on the queue instead. Never silently run with a smaller panel. `lanes.py call` runs its command with a scrubbed environment (the son allowlist; the Anthropic credentials stay only for a Claude command), so a non-Claude voter's own API-key variable must be named in `DTS2_SON_ENV_PASS`. Sons are started by `lanes.py spawn` and only commit; the head pushes and opens each lane's PR with `lanes.py publish <stamp> --lane <lane>`.
7. **State.** Take a stamp, write `.harness/autopilot/<stamp>.md` from the table below, and copy it to `.harness/autopilot/latest.md` after every change. This file, the end-state `## Sections` statuses and the handoff are what `/dt:check-in` reads.

```
# Autopilot <stamp>
panel: claude/opus, <agent>/<model>, <agent>/<model> · tiebreak: claude/fable
council: <five seats> · head: claude/fable
| # | step | branch | plan vote | build vote | council | PR | CI | merged | status |
|---|------|--------|-----------|------------|---------|----|----|--------|--------|
| 1 | section 3: <name> | dts2/<stamp>/step-3 | 3-0 | 2-1 → fable approve | — | #41 | green | 9f3c2a1 | done |
| 2 | section 4: <name> | dts2/<stamp>/step-4 | 3-0 | r1 1-2, r2 2-1, r3 1-2 | 3-2 → head approve (2 updates) | #42 | green | 4b7d0e3 | done |
```
Status is one of `queued`, `planning`, `building`, `voting`, `council`, `pr-open`, `merged`, `done`, `parked (<action-item id>)`, `stopped`.
