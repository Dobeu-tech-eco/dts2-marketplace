---
name: autopilot
description: Run one or more harness steps end to end without stopping for plan or ship approval. A consensus gate replaces the two human checkpoints, three frontier models from different providers must agree on the plan and again on the build, and Claude Fable 5.1 breaks a split. When three rounds of voting still do not settle a step, a council of five frontier reviewers reads the full voting history, votes, writes a brief for every dissent, and Claude Fable 5.1 as head of council makes the final call (more fixes, strike items, or approve) with a written rationale that answers each dissent. Each step gets its own branch and pull request, which is merged once CI is green before the next step starts, so progress is never lost and check-in shows where it stands. Use when the user says autopilot, run these steps without asking, do sections 3 to 5 unattended, or skip plan review.
---

# Autopilot — the harness pipeline with a consensus gate instead of a human

`/dts2-harness:autopilot <steps>` where `<steps>` is any mix of end-state section numbers (`3,4,7` or `3-5`), action-item ids (`D2`, `S1` when the secret is already present), `feature "<description>"`, or quoted free-text tasks. `autopilot resume` continues the last autopilot run. `autopilot status` prints the progress table and stops.

Invoking autopilot is the user's standing approval for exactly the listed steps: their plans, builds, PRs and merges. It is not approval for anything else.

## 0. Pre-check and preflight
1. Run the run skill's **Pre-check (every run command)**. An upgrade it starts stops autopilot; the handoff records `Next action: /dts2-harness:autopilot resume`.
2. Run the run skill's Preflight steps 0–7 (scope, harness-change guard, config, ignore guard, end state, settings, roster, clean tree). Skip its loop-me check-in and the step-8 clarifying question: autopilot asks nothing mid-run.
3. **Resolve the steps** into an ordered queue: sections by their `depends on` order (a listed section whose dependency is neither `done` nor in the queue → park it, see section 4); action items in the order given; a `feature` step runs the feature skill first and its new sections join the queue right after it.
4. **Base and merge target.** `<base>` is `dev` when it exists on the remote. With no `dev`, the base is the default branch, and a merge there is usually a production deploy (Vercel, Lovable, Netlify and similar deploy the default branch). In that case autopilot merges only if the upfront confirmation below names the default branch explicitly and the user says yes; otherwise every step stops at `pr-open` (consensus passed, CI green, PR left for the user), and any later step that depends on it is parked until that PR is merged.
5. **One upfront confirmation, then none.** If any step touches production deploys, data deletion, auth, or payments (the run skill's Preflight step 9), or the merge target is the default branch, list those steps (and `merges go to <default branch>, which deploys production`) and ask once: `Autopilot will plan, build, merge and continue through these without asking again. Go? (y/n)`. None of these → no question. After this point autopilot never waits for the user unless a hard stop below fires.
6. **Voters.** One seat per provider: claude (Opus) always holds the first, then the first two other providers in the probe's `usable` list whose frontier model is set (`roster.py model --agent <name> --tier frontier` is not `null`; for example codex `gpt-6-astra`, gemini, grok, muse), in roster order. An agent with budget `low` is still eligible, since a vote is a `second-opinion` seat. These three are the **panel**. The **council** (section 1b) is five seats spread across as many different frontier providers as possible: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" seats --usable <probe usable, comma-separated>` gives one seat to each usable provider with a frontier model first (claude, codex, gemini, grok, cursor, muse, in that order), and only when there are fewer than five providers does a provider take a second seat, always with a different model (for example Claude Opus 5.5 and Claude Fable 5.0), so no two seats are the same model. A `council:` block in `.harness/config.yaml` changes the defaults: `order: [...]`, `exclude: [...]`, and `models: [provider:model, ...]` for extra frontier models a provider may field (needed for cursor, which has no default frontier model). Each seat says how it is dispatched: `agent-tool` (`dts2-harness:reviewer` with that `model`), `claude-cli` (`claude -p --model <model>` with the ballot), or `roster-command` (`roster.py command --agent <provider> --role second-opinion --tier frontier --model <model> --prompt-file <ballot>`). A seat whose dispatch fails or is classified unavailable is replaced by the first `bench` seat; rerun `seats` with `--failed <provider:model,...>` if the bench is empty. `ok: false` (fewer than five distinct provider/model seats) → the council cannot sit and the step parks. Claude Fable 5.1 is the **head of council** and never holds a council seat. Claude Fable 5.1 is also the **tiebreaker**: dispatched directly with the Agent tool, `subagent_type: dts2-harness:reviewer`, `model: fable`; it never sits on the panel. Fewer than three usable frontier providers → say `Autopilot needs 3 frontier providers; only <n> usable (<names>). Falling back to the normal human checkpoints.` and run `/dts2-harness:run` on the queue instead. Never silently run with a smaller panel.
7. **State.** Take a stamp, write `.harness/autopilot/<stamp>.md` from the table below, and copy it to `.harness/autopilot/latest.md` after every change. This file, the end-state `## Sections` statuses and the handoff are what `/dts2-harness:check-in` reads.

```
# Autopilot <stamp>
panel: claude/opus, <agent>/<model>, <agent>/<model> · tiebreak: claude/fable
council: <five seats> · head: claude/fable
| # | step | branch | plan vote | build vote | council | PR | CI | merged | status |
|---|------|--------|-----------|------------|---------|----|----|--------|--------|
| 1 | section 3: <name> | dts2/<stamp>-s3 | 3-0 | 2-1 → fable approve | — | #41 | green | 9f3c2a1 | done |
| 2 | section 4: <name> | dts2/<stamp>-s4 | 3-0 | r1 1-2, r2 2-1, r3 1-2 | 3-2 → head approve (2 updates) | #42 | green | 4b7d0e3 | done |
```
Status is one of `queued`, `planning`, `building`, `voting`, `council`, `pr-open`, `merged`, `done`, `parked (<action-item id>)`, `stopped`.

## 1. The consensus gate
Used twice per step: on the plan (instead of the Plan checkpoint) and on the built, verified diff (instead of the Ship checkpoint).
1. Write the ballot to `.harness/runs/<stamp>/prompts/vote-<step>-<plan|build>.md`: the step, the end-state excerpt it serves, the lead's plan with its `## Done`, and for the build vote also the diff file, the verifier table and the merged reviewer findings. Ask each voter for exactly one first line `VOTE: APPROVE` or `VOTE: REJECT`, then at most ten findings as `severity file:line — issue — fix`, then any free-form notes.
0. **Keep every note.** Save every response the gate produces, verbatim and in full, to `.harness/runs/<stamp>/votes/<step>/<NN>-<kind>-r<round>-<seat>.md`, where `<NN>` is a running two-digit order number for the step, `<kind>` is `plan`, `build`, `tiebreak`, `fix` (the lead's or builder's note on what a fix round changed and why), `ci` (a CI failure root cause) or `council`, and `<seat>` names the participant (`claude-opus`, `codex-gpt-6-astra`, `claude-fable`, `lead`, `builder-2`). Nothing is summarised or dropped: this folder is the step's full history, and the council reads all of it.
2. Dispatch the three panel voters in one message: claude via the Agent tool (`dts2-harness:reviewer`, `model: opus`); every non-Claude voter via the `shell` of `roster.py command --agent <name> --role second-opinion --tier frontier --prompt-file <ballot>` from the repo, its output classified with `roster.py classify` exactly as the run skill does. A voter that comes back `unavailable (billing/quota)` or `seatFailed`, or whose first line is not a `VOTE:` line, is replaced once by the next usable frontier provider; if none is left, the gate falls back to the human checkpoint for that step only and says so.
3. Count each ballot. There are exactly three outcomes:
   - **3-0 APPROVE** → pass.
   - **REJECT majority** (3-0 or 2-1 REJECT) → not passed. Send the union of the rejecting voters' CRITICAL and HIGH findings to the lead (plan vote) or the owning builders (build vote) as one fix round, then vote again. A REJECT majority is never sent to the tiebreaker: Fable can never pass something most of the panel rejected.
   - **2-1 APPROVE** → send the dissenter's CRITICAL and HIGH findings for one fix round and vote again. A second consecutive 2-1 APPROVE is a **split**.
   - **Split** → dispatch the Fable 5.1 tiebreaker (`dts2-harness:reviewer`, `model: fable`) with the ballot, all three verdicts and their findings. `VOTE: APPROVE` → pass; `VOTE: REJECT` → not passed, treated as a REJECT majority. If the Fable dispatch fails or its first line is not a `VOTE:` line, the split is not passed: that round counts as a failed round and gets a fix round like a REJECT majority. It never defaults to pass, and it never skips straight to the council.
4. **Caps, so the gate always ends.** Every not-passed ballot uses one fix round. Each ballot (the plan vote, then the build vote) gets up to three rounds of the normal vote above, using the run skill's fix-round rules (`/diagnosing-bugs` at round 2 and the fresh pass at round 3); CI-fix rounds (section 3) have their own cap of 3. **The council is never the first answer.** It is convened only when three complete rounds of the normal vote on the same ballot (three panel votes each, plus the tiebreak where one was due) have all failed to pass. Before convening, run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" eligible --votes-dir .harness/runs/<stamp>/votes/<step>`: `eligible: false` → there is no council yet; do what its `reason` says (finish the round, or fix and vote again). Only `eligible: true` lets you convene the **council** (section 1b) instead of parking; the council runs once per step. At the CI-fix cap → park the step (section 4), since no vote can turn a check green.
5. Record every vote, each voter's agent and model, and the tiebreak in the progress table and in the receipt's `### Review verdict` (for example `consensus 3-0 approve (claude/opus, codex/gpt-6-astra, gemini/<model>)`).

## 1b. The council (three rounds of voting did not settle it)
0. **Only after three failed rounds.** `council.py eligible` must have returned `eligible: true` for this step (section 1 step 4). The dossier checks the same rule itself and returns `ok: false` with `eligible: false` and the reason if the normal vote has not failed three complete rounds yet; then go back to the normal vote and do not seat anyone.
1. **Dossier.** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" dossier --votes-dir .harness/runs/<stamp>/votes/<step> --out .harness/runs/<stamp>/prompts/council-<step>-dossier.md`. It joins every saved entry, from the first plan ballot to the last fix note, in order, with every participant's vote, findings and notes. `ok: false` (no entries) → park the step. Write the council ballot to `.harness/runs/<stamp>/prompts/council-<step>.md`: the step, the end-state excerpt, the current plan or diff, the verifier table, and the whole dossier pasted in (never a summary), with the instruction to weigh every round, beginning to end.
2. **Council vote.** Dispatch the five council seats (section 0 step 6) in one message, exactly as panel voters are dispatched. Each answers `VOTE: APPROVE` or `VOTE: REJECT` on the first line, then at most ten findings. Save each response to `.harness/runs/<stamp>/votes/<step>/<NN>-council-r1-<seat>.md` and its own copy to `.harness/runs/<stamp>/council/<step>/<seat>.md`.
3. **Tally.** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" tally .harness/runs/<stamp>/council/<step>/*.md > .harness/runs/<stamp>/council/<step>-tally.json`. Five seats means there is always a majority. Any seat that voted against the majority is a **dissenter** and must include a `## Dissent brief`: why it disagrees, which round or note in the history supports that, and the specific update that would resolve it, in at most 200 words. A dissenter listed in `missingBrief` is sent back once to write it; a seat that still returns no valid vote or brief is replaced once by the first `bench` seat from `council.py seats`. Still not five valid ballots with every brief → park the step.
4. **Head of council.** Dispatch Claude Fable 5.1 (`dts2-harness:reviewer`, `model: fable`) with the council ballot, the full dossier, all five council responses, every dissent brief and the tally. It has the final word and three choices, written to `.harness/autopilot/council-<stamp>-<step>.md`:
   - `DECISION: FIX` — run more fixes. `## Fixes` lists each fix and its owning builder (or the lead, on a plan).
   - `DECISION: STRIKE` — remove items from the step. `## Struck` lists each plan item or diff hunk taken out; each becomes a Decisions action item so nothing is silently lost, and the rest of the step continues.
   - `DECISION: APPROVE` — pass the step, provided every dissent is answered and the updates it calls for are made.
   Every decision record must have `## Head of council brief` (what it decided and why, in plain language for the user), `## History considered` with the line `Entries reviewed: <the dossier's entries count>` and the rounds and notes that drove the call, and `## Dissent responses` with a `### <seat>` block for every dissenter stating how the dissent is addressed and an `Update:` line naming the change made for it (or, for a dissent it overrules, the change that answers the concern). It may decide against the council majority, but only through those responses.
5. **Check the record.** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" check-decision .harness/autopilot/council-<stamp>-<step>.md --tally .harness/runs/<stamp>/council/<step>-tally.json --entries <entries>`. `ok: false` → send the `problems` back to the head once; still not ok → park the step. A head dispatch that fails, or a record with no `DECISION:` line, never defaults to a pass.
6. **Carry it out.** The fixes, the strikes, and the updates named in `Update:` lines go to the owning builders (or the lead) as at most two head-of-council fix rounds, each followed by the verifier and a confirmation dispatch to the head with the new diff, which answers `VOTE: APPROVE` when every listed change landed. All of it is saved to the votes folder as more entries. Approved → the step passes this gate and continues (a build pass goes to section 3). Not approved after the second round → park the step. These rounds do not reopen the 3-round cap and the council does not reconvene for the same step.
7. **Record it in the harness.** Whatever the outcome (pass or park), run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" ledger --ballots-dir .harness/runs/<stamp>/council/<step> --tally .harness/runs/<stamp>/council/<step>-tally.json --decision .harness/autopilot/council-<stamp>-<step>.md --step <step> --stamp <stamp> --out .harness/council.md`. It appends to `.harness/council.md` the council vote, every member's vote with its reasons and dissent brief verbatim, the final decision, the head of council's brief, its dissent responses, fixes and strikes. Then add one line to `.harness/state.md` under `## Council decisions` (`<stamp> <step>: council <a>-<r> → head <decision>, see .harness/council.md`), and append the brief's lesson to `.harness/lessons.md` as `council <stamp> <step>: <what the head decided and why, one line>` so later plans and the lead learn from it. `.harness/council.md` and the decision record are committed on the step branch with the step's changes, so the history lives in the repo, not only in the run folder.
8. **Tell the user.** The decision record is the explanation of why autopilot went the way it did. Record `council <approve>-<reject> → head <decision>` in the table's council cell and the receipt's `### Review verdict`, put the record's `## Head of council brief` and `## Dissent responses` in the PR's Consensus section, and link the record in the handoff and the final report.

## 2. Per step: plan, build, verify, vote
For each queued step, in order:
1. **Branch** from the freshly fetched base: `git fetch origin` then `git switch -c dts2/<stamp>-<step> origin/<base>` (`dev` when it exists, else the default branch). Never build on a previous step's unmerged branch.
2. Run the run skill's Phase 0 (size, budget), Phase 1 (lead plan) and the **plan vote** in place of the Plan checkpoint. A `feature` step is a step like any other: the feature skill's plan patch is the plan, its approval questions are answered by the plan vote, its PR goes through section 3 and is merged before the sections it added are planned, so they branch from a base that already contains them.
3. Run Phases 2, 3, 3b and 3c exactly as the run skill does: parallel builders on separate file sets in worktrees, never a frontier builder, the walkthrough, axis reviews, the final review, the verifier. Verifier BLOCKED is a not-passed build; it gets the normal fix rounds. A value the builder needs and the user has not supplied (a secret, a decision, a paid side effect) is filed as a user-input item with its `TASK_` link (section 4) and the build keeps going: wired by name, mocked in tests.
4. Run the **build vote** in place of the Ship checkpoint.
5. Fill the receipt as the run skill's Phase 4 does, with `### Approved by` set to `autopilot consensus (<votes>), <YYYY-MM-DD>` and do the run skill's **After ship** writes (lessons, end-state acceptance boxes, section status `in-progress`, state.md, handoff). The evolve sweep is not run inside autopilot; open harness lessons are listed in the final report.
6. **Bundle**. A step may carry up to `MAX_BUNDLE` (5) queued tasks of the same section on one branch and one PR when they share no file and none depends on an unmerged step; the head assigns the bundle in the brief, never the builder. Each task ends in its own checkpoint commit `dts2(<lane>): checkpoint <k>/<n> <task>` after its own verifier pass, and the run dir's `status.json` lists them under `"checkpoints"`, so a stopped bundle resumes at the last passed checkpoint instead of the first task. A question raised mid-bundle is a ballot like any other; a task that parks drops out of the bundle and the rest ships.

## 3. Per step: PR, CI, merge
1. Commit with a Conventional Commits message, after the setup-pre-commit gate the run skill names. Push the step branch (`git push -u origin dts2/<stamp>-<step>`; never force, never to `main` or `dev`).
2. Open the PR the way `/dts2-harness:ship` steps 5–6 do (template, `/pr`, receipt), with the template's **Consensus** section filled from the votes. Then post the three verdicts, the tiebreak if any, the council decision record if the step went to council, and the receipt as a PR comment (`gh pr comment <n> --body-file <file>`) so the merge carries visible review evidence.
3. Watch CI: `gh pr checks <n> --watch`, 30-minute cap. A red check → collect `gh run view <id> --log-failed`, send the root cause to the owning builder as a fix round (same 3-round cap), push the fix (a new commit, never a force-push), and run the **build vote** again on the new diff before re-watching CI. A Vercel preview canceled only because a commit is unsigned is non-blocking, as the run skill says.
4. **Merge** when CI is green, the latest build vote passed, and the merge target is allowed (preflight step 4): read the base's protection (`gh api repos/<owner>/<repo>/branches/<base>/protection`); `required_linear_history` or no preference → `gh pr merge <n> --squash --delete-branch`; never `--admin`, never bypass a required review or check. If the merge is refused (a required human review, a missing required check, a permission or tool denial) → do not work around it: park the step with a Decisions action item `merge PR #<n> (autopilot consensus passed, CI green)` and stop every step that depends on it; independent steps continue.
5. After the merge: `git fetch origin`, record the merge SHA in the table, set the section's status to `done` in `.harness/end-state.md` (tick its acceptance boxes the verifier confirmed) on the next step's branch, refresh `.harness/handoff/latest.md` with `Next action: /dts2-harness:autopilot resume`, and remove the step's worktrees and local branches.
6. **Post-merge check**. Nothing is `done` on the merge alone. Dispatch `dts2-harness:verifier` with `Mode: post-merge` and the merge SHA against production when the merge deploys there, else against a server started from the merged base; it walks every screen the step's `Done` lines name and returns `walkthrough PASS n/n`. PASS → the section is `done`. FAIL → one fix round on a new branch from the merged base, then the vote and this check again. No browser available → park the step with a Decisions item `post-merge walkthrough <step>`; the step is never `done` on a skipped walkthrough, and the verifier must never SKIP it.

## 4. Parking, hard stops, and resume
- **Park** (the step stops, the run continues with steps that do not depend on it): fix-round cap reached, merge refused, a dependency parked, a handoff-only builder, a voter-pool collapse for that step, or a council that could not seat five valid ballots, produce a valid decision record, or confirm its changes. A pre-check that reports a skill gone upstream never swaps under autopilot: it becomes a Decisions action item listing the ranked candidates, for the user to approve later. Each park gets an action item (Secrets, Decisions or Handoff), its id in the table's status and in the section cell (`payments webhook (D4)`).
- **User-input items never park.** A missing value the user must supply never slows or stops a task: the builder wires it by name, tests mock it, and the item is filed with `action-items.py add <group> "<title>" --task <onboard task id>` so its row reads `TASK_<task>_<item id>-<title>` (`TASK_A1_S2-stripe secret`). `action-items.py done <id>` prints the linked task so the resume knows which PR it unblocks. The task builds, votes and opens its PR as normal; what it cannot do is merge (section 5a).
- **Hard stop** (the whole autopilot stops, handoff written, `.harness/autopilot/latest.md` status `stopped`): the context guard fires; a change would touch a `do_not_touch` path; a step would deploy to production (other than a default-branch merge the step-5 confirmation approved by name), delete data, force-push, rewrite published history, or push to `main`/`dev` directly; a pre-check upgrade; the user interrupts.
- `autopilot resume` reads `.harness/autopilot/latest.md` and continues at the first step that is not `done` or `parked`, re-running the pre-check first.

## 5a. Adjudication
Every run, `autopilot` or `fullauto`, ends the same way: before the final report, present every open user-input item to the user together, grouped by the PR it blocks, not one at a time as they were filed.
- A PR whose completion needs a value the user has not supplied (a database to create, a secret to use or share, a paid side effect) stays at `pr-open`: it is never merged and its section is never `done` while an item on it is open. Its body carries `## Blocked by` listing the `TASK_` items; the lane's `status.json` has `"status": "blocked"`, `"reason": "awaiting-items"` and `"blocked_by": [<item ids>]`.
- Keep the open PRs at the end to as few as the feasibility test allows: bundle blocked tasks of the same section onto one PR (section 2 step 6, no file overlap, at most `MAX_BUNDLE`) rather than one PR per task, and before the ledger is written fold non-conflicting blocked lanes into one PR. Never split a blocked PR to make the ledger look shorter; a long list of tasks on one open PR beats many open PRs.
- Write and print the task ledger: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/task-ledger.py" <stamp>` produces `.harness/runs/<stamp>/task-ledger.md`, one row per open PR (number, branch, bundled tasks, blocking item ids and titles) and the count line `N open PRs, M blocking items`. Link it from `.harness/state.md` and the final report.
- When the user marks an item done, the next run or `resume` runs `task-ledger.py <stamp> --resolved` first; every PR it lists (all of its items done) is rebased on the fetched base, re-verified, and merged through section 3 and its post-merge check, and its row becomes `merged`.
- `fullauto` stops only when nothing is outstanding and every lane is `done`, or `blocked` with its items in the ledger.

## 5. Final report
Print the progress table, then one line each: steps done, parked (with action-item ids and the command that unblocks each), PRs merged, council decisions (one line each: step, tally, decision, path to the record so the user can read the rationale), branches left (should be only `main` and `dev`; run `/dts2-harness:ship` step 7's sweep with autopilot's no-ask rule if any step branch survived), open harness lessons for the evolve sweep, the task ledger (`.harness/runs/<stamp>/task-ledger.md`, its count line and each open PR with its blocking items), and `/dts2-harness:check-in` for the full picture.

## 6. Son mode
`/dts2-harness:autopilot --son <stamp>/<lane>` is one headless lane of a `dpp` run, started by the head in the lane's worktree. Everything in sections 0 to 5a applies unchanged; `discipline.md` and the run and ship skills are the rules, this section only says what differs.
- Input: `.harness/runs/<stamp>/<lane>/brief.md` (lane id, branch `dts2/<stamp>/<lane>`, file set, task list, `MAX_BUNDLE`). Output: `status.json`, `report.md` and the receipts in that run dir, nothing else under `.harness/`; `harness-lock.py --role son` refuses the shared records, which the head folds on completion.
- A question goes to `questions/<n>.md` in the run dir and the son waits for the head's answer file; the head answers alone. A son talks to the head, never the user.
- The son takes a step through to `pr-open` and waits for `merge-go.md` from the head before section 3 step 4; the head serialises merges across lanes.
- A son never runs setup or onboard, never writes `.harness/lessons.md` (lessons go in `report.md` for the head), never starts another son, and never runs `dpp`.
- A son that has not written `status.json` within `builder_timeout_min` is reported `incomplete`, reason `stalled`, by the head.

## Guardrails
- The council is an escalation, not a shortcut: it sits only after three complete rounds of the normal vote on the same ballot have failed (`council.py eligible`), never earlier and never because one dispatch failed.
- The panel is always three distinct providers at frontier; Fable 5.1 only ever breaks a tie or heads the council. No consensus or council decision, no merge.
- Council seats are always five distinct provider/model pairs, as many providers as are usable; a provider holds a second seat only with a different model, and never with Fable 5.1.
- Every council is written to `.harness/council.md`, `.harness/state.md` and `.harness/lessons.md`: the vote, each member's reasons, the decision and the head's brief.
- The council and its head always get the full history: every round, every ballot, every note from every participant, start to finish. Nothing is summarised away.
- A council decision never overrides a hard stop, a `do_not_touch` path, or branch protection.
- Builders never run a frontier model; frontier is for the votes, the lead, the final review and the verifier, as in the run skill.
- One PR per step or bundle, merged before the next step branches from the updated base, so a stopped run loses at most the step in flight; a PR blocked on a user-input item is the one exception and waits at `pr-open`.
- Never deploy, delete data, force-push, use `--admin`, or bypass branch protection. A tool or policy denial is a park, never something to route around.
- Never print a secret's value.
- A missing user-supplied value is never a reason to stop (section 4); it is a reason for the PR to wait (section 5a), and the run ends with as few open PRs as the bundle rule allows.
