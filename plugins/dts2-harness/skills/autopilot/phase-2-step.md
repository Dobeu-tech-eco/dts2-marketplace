# autopilot - sections 2 and 3, per step: build, vote, PR, CI, merge

## 2. Per step: plan, build, verify, vote
For each queued step, in order:
1. **Branch** from the freshly fetched base: `git fetch origin` then `git switch -c dts2/<stamp>/step-<step> origin/<base>` (`dev` when it exists, else the default branch). Never build on a previous step's unmerged branch.
2. Run the run skill's Phase 0 (size, budget), Phase 1 (lead plan) and the **plan vote** in place of the Plan checkpoint. A `feature` step is a step like any other: the feature skill's plan patch is the plan, its approval questions are answered by the plan vote, its PR goes through section 3 and is merged before the sections it added are planned, so they branch from a base that already contains them.
3. Run Phases 2, 3, 3b and 3c exactly as the run skill does: parallel builders on separate file sets in worktrees, never a frontier builder, the walkthrough, axis reviews, the final review, the verifier. Verifier BLOCKED is a not-passed build; it gets the normal fix rounds. A value the builder needs and the user has not supplied (a secret, a decision, a paid side effect) is filed as a user-input item with its `TASK_` link (section 4) and the build keeps going: wired by name, mocked in tests.
4. Run the **build vote** in place of the Ship checkpoint.
5. Fill the receipt as the run skill's Phase 4 does, with `### Approved by` set to `autopilot consensus (<votes>), <YYYY-MM-DD>` and do the run skill's **After ship** writes (lessons, end-state acceptance boxes, section status `in-progress`, state.md, handoff). The evolve sweep is not run inside autopilot; open harness lessons are listed in the final report.
6. **Bundle**. A step may carry up to `MAX_BUNDLE` (5) queued tasks of the same section on one branch and one PR when they share no file and none depends on an unmerged step; the head assigns the bundle in the brief, never the builder. Each task ends in its own checkpoint commit `dts2(<lane>): checkpoint <k>/<n> <task>` after its own verifier pass, and the run dir's `status.json` lists them under `"checkpoints"`, so a stopped bundle resumes at the last passed checkpoint instead of the first task. A question raised mid-bundle is a ballot like any other; a task that parks drops out of the bundle and the rest ships.

## 3. Per step: PR, CI, merge
1. Commit with a Conventional Commits message, after the setup-pre-commit gate the run skill names. Push the step branch (`git push -u origin dts2/<stamp>/step-<step>`; never force, never to `main` or `dev`).
2. Before creating the PR, run `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py" reconcile <stamp> --step <step>` (a son skips this call and follows `son-mode.md`): if GitHub already has a PR for the branch (`adopt-pr`) or already merged it (`merged`), use that and do not create another. Open the PR the way `/dts2:ship` steps 5–6 do (template, `/pr`, receipt), with the template's **Consensus** section filled from the votes. Then post the three verdicts, the tiebreak if any, the council decision record if the step went to council, and the receipt as a PR comment (`gh pr comment <n> --body-file <file>`) so the merge carries visible review evidence.
3. Watch CI: `gh pr checks <n> --watch`, 30-minute cap. A red check → collect `gh run view <id> --log-failed`, send the root cause to the owning builder as a fix round (same 5-round cap), push the fix (a new commit, never a force-push), and run the **build vote** again on the new diff before re-watching CI. A Vercel preview canceled only because a commit is unsigned is non-blocking, as the run skill says.
4. **Merge** (run `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py" reconcile <stamp> --step <step>` first, skipped by a son, which never merges; `merged` means skip the merge) when CI is green, the latest build vote passed, and the merge target is allowed (preflight step 4): read the base's protection (`gh api repos/<owner>/<repo>/branches/<base>/protection`); `required_linear_history` or no preference → first fetch, read the PR head with `gh pr view <n> --json headRefOid`, and grant the merge with `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py" merge-go-step <stamp> --step <step> --head <that sha>` (it records the head and the current tip of the base; refused inside a son, and for the default branch without the recorded yes), then `gh pr merge <n> --squash --delete-branch`; if the base moves before the merge runs, fetch and grant again; never `--admin`, never bypass a required review or check. If the merge is refused (a required human review, a missing required check, a permission or tool denial) → do not work around it: park the step with a Decisions action item `merge PR #<n> (autopilot consensus passed, CI green)` and stop every step that depends on it; independent steps continue.
5. After the merge: `git fetch origin`, record the merge SHA in the table, set the section's status to `done` in `.harness/end-state.md` (tick its acceptance boxes the verifier confirmed) on the next step's branch, refresh `.harness/handoff/latest.md` with `Next action: /dts2:autopilot resume`, and remove the step's worktrees and local branches.
6. **Post-merge check**. Nothing is `done` on the merge alone. Dispatch `dts2:verifier` with `Mode: post-merge` and the merge SHA against production when the merge deploys there, else against a server started from the merged base; it walks every screen the step's `Done` lines name and returns `walkthrough PASS n/n`. PASS → the section is `done`. FAIL → record it with `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py" walkthrough-failed <stamp> --lane <lane> --reason "..."` (it files the revert action item), then one fix round on a new branch from the merged base, then the vote and this check again. No browser available → park the step with a Decisions item `post-merge walkthrough <step>`; the step is never `done` on a skipped walkthrough, and the verifier must never SKIP it.
   A post-merge verifier report whose first line is `PARTIAL: hit turn cap at <step>` is no verdict: the step is not `done`; re-dispatch with a narrower scope or a fresh agent, inside the fix-loop cap.
