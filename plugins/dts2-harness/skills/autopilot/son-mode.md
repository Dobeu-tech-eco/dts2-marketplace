# autopilot - section 6, son mode

## 6. Son mode
`/dt:autopilot --son <stamp>/<lane>` is one headless lane of a `dpp` run, started by the head in the lane's worktree. Everything in sections 0 to 5a applies unchanged, except section 3 steps 2 and 4 (below); `discipline.md` and the run and ship skills are the rules, this section only says what differs.
- Input: `.harness/runs/<stamp>/<lane>/brief.md` (lane id, lease epoch, branch `dts2/<stamp>/lane-<lane>`, file set, task list, `MAX_BUNDLE`), which the head builds with `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/briefs.py" son-brief <manifest> --lane <lane> --epoch <epoch> --out <brief.md>`; a son reads the brief and this file first, then the other phase files (gate, step, parking) on demand as it reaches each section. The discipline, roster and probe arrive in the system prompt (`briefs.py prefix`), not as files to read. Output: `status.json`, `report.md` and the receipts in that run dir, nothing else under `.harness/`; `harness-lock.py --role son` refuses the shared records, which the head folds on completion.
- Builder branches: inside a son, builder `<n>` gets `git worktree add "$DTS2_BUILDERS_DIR/<n>" -b dts2/<stamp>/lane-<lane>-b<n> dts2/<stamp>/lane-<lane>` (`DTS2_BUILDERS_DIR` is the one directory outside the repo that `lanes.py spawn` creates and the sandbox lets the son write; a worktree anywhere else is refused), and the son merges builder branches into `dts2/<stamp>/lane-<lane>`, not `dts2/<stamp>/main`.
- A son never runs `lanes.py reconcile` (it refuses inside a son: the head alone reconciles, on resume and before every merge), so it skips the reconcile calls in section 3 steps 2 and 4. A son hands over a committed branch only (Q1): in section 3 it does steps 1 (commit, with no push), skips step 2 (the PR), step 3 (CI watch), step 4 (merge) and step 6, and stops. The head pushes the lane branch, opens one PR per lane, watches CI, merges after the verifier passed and runs the post-merge check; `gh` is not available to a son at all.
- A son runs under the sandbox, a tool allowlist (file tools, `git add`, `git commit`, the repo's check commands, the harness scripts) and a deny hook: it never pushes, never runs `gh pr` or `gh api`, never merges, never runs `lanes.py merge-go`, `merge-go-step`, `merge-target` or `gc-restore` (by any path, `python3 lanes.py` or the file itself), never reads credentials, and never writes `.claude/` (the person's approvals live in `.claude/settings.local.json`), `.mcp.json`, `.git/hooks` or `merge-go.md`. A lane diff that touches a protected file (workflows, `.gitattributes`, `.git` internals, CODEOWNERS, `hooks/`, the checks script, head-only `.harness` records) is not published: the head parks the lane and files a Decisions item (`scripts/protected.py`). A denial is a park, not something to route around.
- A question goes to `questions/<n>.md` in the run dir and the son waits for the head's answer file; the head answers alone. A son talks to the head, never the user.
- The son takes a step through to a committed branch with green checks and stops with `--status pr-open` (the phase name is unchanged: it means the branch is ready for the head to publish). It never runs section 3 step 4 or step 6. The head runs `scripts/head_publish.py` (push, one PR per lane), grants `merge-go.md` (an internal head step; a son never sees it), merges through the merge guard only when the unattended-merge preconditions hold (checks reported and green, required checks and a review or a merge queue on the default branch, the person's per-PR yes when the merge deploys production), and serialises merges across lanes. Before launch the head bootstraps each lane (`head_publish.py bootstrap`: one idempotent install, a sanitized env file of non-secret keys, missing secret names filed as Secrets items); a son is never handed a secret.
- A son never runs setup or onboard, never writes `.harness/lessons.md` (lessons go in `report.md` for the head), never starts another son, and never runs `dpp`.
- Each builder step a son runs is recorded with `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py" builder <stamp> --lane <lane> --section <n> --branch <builder branch> --status <status> [--sha <sha>] [--pr <n>]`.
- A son stamps its heartbeat at every turn boundary with `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py" heartbeat <stamp> --lane <lane>`. A son sets its phase only through the script, never by writing `status.json` (`lanes.py heartbeat --status` and `python3 -I "${CLAUDE_PLUGIN_ROOT}/scripts/lanes.py" transition <stamp> --lane <lane> --to <phase>` go through the same table of legal moves, and a son may only report `pr-open`, `done`, `blocked` or `incomplete`; `starting` and `orphaned` are the head's): `lanes.py heartbeat <stamp> --lane <lane> --status pr-open` while it waits for `merge-go.md`, then `--status done`, `--status blocked` or `--status incomplete` (with `--reason "..."`) at the end. `lanes.py status` marks a lane with no heartbeat for `stall_minutes` stalled, unless its son process is still running; the head never edits `status.json` itself.
