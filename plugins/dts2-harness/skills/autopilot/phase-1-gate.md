# autopilot - sections 1 and 1b, the consensus gate and the council

## 1. The consensus gate
Used twice per step: on the plan (instead of the Plan checkpoint) and on the built, verified diff (instead of the Ship checkpoint).
1. Write the ballot to `.harness/runs/<stamp>/prompts/vote-<step>-<plan|build>.md`: the step, the end-state excerpt it serves, the lead's plan with its `## Done`, and for the build vote also the diff file, the verifier table and the merged reviewer findings. Ask each voter for exactly one first line `VOTE: APPROVE` or `VOTE: REJECT`, then at most ten findings as `severity file:line — issue — fix`, then any free-form notes.
   **Checks before votes (build vote).** Before the ballot goes out, record the base the step branched from in `.harness/runs/<stamp>/base` (one ref) and run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/checks.py" run --stamp <stamp>`; it covers tests, typecheck, lint, secret scan and scope check, each as one ledger line. Any red or missing check means a fix round and zero votes: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" route --ledger .harness/runs/<stamp>/ledger.jsonl --head <sha>` (`<sha>` is `git rev-parse HEAD`, so results from an older commit count as missing) must return `action: vote` before step 2, and after the votes it is called again with `--votes A,B,C` to decide the next move. When voters choose between several competing proposals, build the ballots with `council.py blind --proposals <dir> --out <dir> --voters <seats> --seed <stamp>-<step> --ledger .harness/runs/<stamp>/ledger.jsonl`, so no ballot names its author and each voter sees its own option order. The plan vote has no code to check and skips the checks.
0. **Keep every note.** Save every response the gate produces, verbatim and in full, to `.harness/runs/<stamp>/votes/<step>/<NN>-<kind>-r<round>-<seat>.md`, where `<NN>` is a running two-digit order number for the step, `<kind>` is `plan`, `build`, `tiebreak`, `fix` (the lead's or builder's note on what a fix round changed and why), `ci` (a CI failure root cause) or `council`, and `<seat>` names the participant (`claude-opus`, `codex-gpt-6-astra`, `claude-fable`, `lead`, `builder-2`). Nothing is summarised or dropped: this folder is the step's full history, and the council reads all of it.
2. Dispatch the three panel voters in one message: claude via the Agent tool (`dts2-harness:reviewer`, `model: opus`); every non-Claude voter through the call limit: get its argv with `roster.py command --agent <name> --role second-opinion --tier frontier --prompt-file <ballot>` (it only prints), then run those words (the output's `env` pairs after `env`, then its `argv`) as `lanes.py call <stamp> --label <seat> --cost-source none --out <file> --prompt-file <the output's stdin path, when it has one> -- <those words>` from the repo, so the voter shares the global call limit, backoff and spend counter; classify the output file with `roster.py classify` exactly as the run skill does. The Agent-tool voter cannot be routed through `lanes.py call`, so it sits outside the call limit and the spend counter; say so in the run report. A voter that comes back `unavailable (billing/quota)` or `seatFailed`, or whose first line is not a `VOTE:` line, is replaced once by the next usable frontier provider; if none is left, the gate falls back to the human checkpoint for that step only and says so.
   A voter report whose first line is `PARTIAL: hit turn cap at <step>` is no vote: it is not an approval, a rejection or a split; re-dispatch that voter with a narrower scope or a fresh agent, inside the fix-loop cap.
3. Count each ballot. There are exactly three outcomes:
   - **3-0 APPROVE** → pass.
   - **REJECT majority** (3-0 or 2-1 REJECT) → not passed. Send the union of the rejecting voters' CRITICAL and HIGH findings to the lead (plan vote) or the owning builders (build vote) as one fix round, then vote again. A REJECT majority is never sent to the tiebreaker: Fable can never pass something most of the panel rejected.
   - **2-1 APPROVE** → send the dissenter's CRITICAL and HIGH findings for one fix round and vote again. A second consecutive 2-1 APPROVE is a **split**.
   - **Split** → dispatch the Fable 5.1 tiebreaker (`dts2-harness:reviewer`, `model: fable`) with the ballot, all three verdicts and their findings. `VOTE: APPROVE` → pass; `VOTE: REJECT` → not passed, treated as a REJECT majority. If the Fable dispatch fails or its first line is not a `VOTE:` line, the split is not passed: that round counts as a failed round and gets a fix round like a REJECT majority. It never defaults to pass, and it never skips straight to the council.
   - A tiebreaker report whose first line is `PARTIAL: hit turn cap at <step>` is no vote: re-dispatch it with a narrower scope or a fresh agent, inside the fix-loop cap.
4. **Caps, so the gate always ends.** Every not-passed ballot uses one fix round. Each ballot (the plan vote, then the build vote) gets up to three rounds of the normal vote above, using the run skill's fix-round rules (`/diagnosing-bugs` at round 2 and the fresh pass at round 3); CI-fix rounds (section 3) have their own cap of 3. **The council is never the first answer.** It is convened only when three complete rounds of the normal vote on the same ballot (three panel votes each, plus the tiebreak where one was due) have all failed to pass. Before convening, run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" eligible --votes-dir .harness/runs/<stamp>/votes/<step>`: `eligible: false` → there is no council yet; do what its `reason` says (finish the round, or fix and vote again). Only `eligible: true` lets you convene the **council** (section 1b) instead of parking; the council runs once per step. At the CI-fix cap → park the step (section 4), since no vote can turn a check green.
5. Record every vote, each voter's agent and model, and the tiebreak in the progress table and in the receipt's `### Review verdict` (for example `consensus 3-0 approve (claude/opus, codex/gpt-6-astra, gemini/<model>)`).

## 1b. The council (three rounds of voting did not settle it)
0. **Only after three failed rounds.** `council.py eligible` must have returned `eligible: true` for this step (section 1 step 4). The dossier checks the same rule itself and returns `ok: false` with `eligible: false` and the reason if the normal vote has not failed three complete rounds yet; then go back to the normal vote and do not seat anyone.
1. **Dossier.** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" dossier --votes-dir .harness/runs/<stamp>/votes/<step> --out .harness/runs/<stamp>/prompts/council-<step>-dossier.md`. It joins every saved entry, from the first plan ballot to the last fix note, in order, with every participant's vote, findings and notes. `ok: false` (no entries) → park the step. Write the council ballot to `.harness/runs/<stamp>/prompts/council-<step>.md`: the step, the end-state excerpt, the current plan or diff, the verifier table, and the whole dossier pasted in (never a summary), with the instruction to weigh every round, beginning to end.
2. **Council vote.** Dispatch the five council seats (section 0 step 6) in one message, exactly as panel voters are dispatched. Each answers `VOTE: APPROVE` or `VOTE: REJECT` on the first line, then at most ten findings. Save each response to `.harness/runs/<stamp>/votes/<step>/<NN>-council-r1-<seat>.md` and its own copy to `.harness/runs/<stamp>/council/<step>/<seat>.md`.
3. **Tally.** Ballots are untrusted: the first line must be exactly `VOTE: APPROVE|REJECT` (or a JSON object whose only key is `verdict`), and a ballot with a second verdict line or any other first line is invalid. `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" tally .harness/runs/<stamp>/council/<step>/*.md > .harness/runs/<stamp>/council/<step>-tally.json`. Five seats means there is always a majority. Any seat that voted against the majority is a **dissenter** and must include a `## Dissent brief`: why it disagrees, which round or note in the history supports that, and the specific update that would resolve it, in at most 200 words. A dissenter listed in `missingBrief` is sent back once to write it; a seat that still returns no valid vote or brief is replaced once by the first `bench` seat from `council.py seats`. Still not five valid ballots with every brief → park the step.
4. **Head of council.** Dispatch Claude Fable 5.1 (`dts2-harness:reviewer`, `model: fable`) with the council ballot, the full dossier, all five council responses, every dissent brief and the tally. It has the final word and three choices, written to `.harness/autopilot/council-<stamp>-<step>.md`:
   A head-of-council report whose first line is `PARTIAL: hit turn cap at <step>` is no decision: re-dispatch with a narrower scope or a fresh agent, inside the fix-loop cap.
   - `DECISION: FIX` — run more fixes. `## Fixes` lists each fix and its owning builder (or the lead, on a plan).
   - `DECISION: STRIKE` — remove items from the step. `## Struck` lists each plan item or diff hunk taken out; each becomes a Decisions action item so nothing is silently lost, and the rest of the step continues.
   - `DECISION: APPROVE` — pass the step, provided every dissent is answered and the updates it calls for are made.
   Every decision record must have `## Head of council brief` (what it decided and why, in plain language for the user), `## History considered` with the line `Entries reviewed: <the dossier's entries count>` and the rounds and notes that drove the call, and `## Dissent responses` with a `### <seat>` block for every dissenter stating how the dissent is addressed and an `Update:` line naming the change made for it (or, for a dissent it overrules, the change that answers the concern). It may decide against the council majority, but only through those responses.
5. **Check the record.** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" check-decision .harness/autopilot/council-<stamp>-<step>.md --tally .harness/runs/<stamp>/council/<step>-tally.json --entries <entries>`, plus `--ledger .harness/runs/<stamp>/ledger.jsonl --head <sha>` only when the council sits on the build ballot. A plan-ballot council omits `--ledger`: a plan has no check records, so the ledger would refuse every approval. `ok: false` → send the `problems` back to the head once; still not ok → park the step. A head dispatch that fails, or a record with no `DECISION:` line, never defaults to a pass.
6. **Carry it out.** The fixes, the strikes, and the updates named in `Update:` lines go to the owning builders (or the lead) as at most two head-of-council fix rounds, each followed by the verifier and a confirmation dispatch to the head with the new diff, which answers `VOTE: APPROVE` when every listed change landed. On the build ballot only, after each fix round and before the confirmation dispatch, run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/checks.py" run --stamp <stamp>` and then `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" route --ledger .harness/runs/<stamp>/ledger.jsonl --head <sha>`; any result other than `action: vote` means the round is not approved, no confirmation is sent, the round still counts, and the step parks after the second round. All of it is saved to the votes folder as more entries. Approved → the step passes this gate and continues (a build pass goes to section 3). Not approved after the second round → park the step. These rounds do not reopen the 3-round cap and the council does not reconvene for the same step.
7. **Record it in the harness.** Whatever the outcome (pass or park), run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/council.py" ledger --ballots-dir .harness/runs/<stamp>/council/<step> --tally .harness/runs/<stamp>/council/<step>-tally.json --decision .harness/autopilot/council-<stamp>-<step>.md --step <step> --stamp <stamp> --out .harness/council.md`. It appends to `.harness/council.md` the council vote, every member's vote with its reasons and dissent brief verbatim, the final decision, the head of council's brief, its dissent responses, fixes and strikes. Then add one line to `.harness/state.md` under `## Council decisions` (`<stamp> <step>: council <a>-<r> → head <decision>, see .harness/council.md`), and append the brief's lesson to `.harness/lessons.md` as `council <stamp> <step>: <what the head decided and why, one line>` so later plans and the lead learn from it. `.harness/council.md` and the decision record are committed on the step branch with the step's changes, so the history lives in the repo, not only in the run folder.
8. **Tell the user.** The decision record is the explanation of why autopilot went the way it did. Record `council <approve>-<reject> → head <decision>` in the table's council cell and the receipt's `### Review verdict`, put the record's `## Head of council brief` and `## Dissent responses` in the PR's Consensus section, and link the record in the handoff and the final report.
